📚 Cubby, on one page

A shelf of tiny web apps, each in its own cubby. This page is everything you need to understand the platform, use its APIs, and run your own. It is itself a cubby app.

In a nutshell

One GitHub repo deploys to one PocketHost (PocketBase) instance and hosts many tiny static web apps. Each app is a directory of plain html/js/css: no build step, no framework, no server code of its own.

repo
pb_public/<app>/ + hooks + migrations
deploys to
instance
<name>.pockethost.io
serves
/<app>/
+ / discovery site

Every app loads core, then whatever else it actually uses:

<script src="/js/core.js" defer></script>
<script src="/js/platform.js" defer></script>

Those expose a global cubby object providing a database (db), file storage (fs), OAuth login (identity), AI chat (ai), and multi-user rooms (rooms), all backed by the shared PocketBase instance; markdown rendering and editing (markdown) is one more opt-in script tag. The root of every deployment is a discovery site listing its apps. Login state is shared across all apps on the origin: sign in once, signed in everywhere.

How a request flows

Hover a journey below the diagram — or tab to it — to trace one path through the platform. Every journey is written out underneath, so the drawing is never the only copy.

What it's good for

Weekend-sized ideas that deserve to stay alive: guestbooks, timers, trackers, polls, little games, dashboards, gifts. Anything where "a static page plus a database plus login" covers it, and where shipping in an afternoon beats architecture. New app cost is one directory, so nothing stops you from having thirty of them.

Honest constraints, by design:

  • Rooms ride PocketBase realtime over SSE: expect 100-500ms latency. Chat, presence, and casual multiplayer are great; twitch gameplay is not.
  • AI chat is non-streaming (the server hook buffers whole responses).
  • Apps are static files; anything dynamic goes through the foundation APIs.
  • Write isolation between apps is convention, not enforcement: a single-operator platform.

The Claude plugin

The repo is its own Claude Code plugin marketplace. The skills that power it are the same documents an AI agent follows, so "ask Claude to do it" is a first-class path:

There is also an issue-to-app pipeline: label a GitHub issue new-app and a bundled workflow has Claude build it as a pull request; merging deploys it. Idea on your phone to live app, no laptop involved.

Modules and load order

cubby ships in layers so a page pays only for what it uses. core.js is the namespace, errors, escaping and the widget lifecycle — no PocketBase at all. platform.js adds db, fs, identity, ai and rooms. Everything else layers on top of core, and most of it never touches the backend, so a page that only renders content can skip platform.js entirely.

bundlegzneedswhat it is
core.js1.6KB—namespace, CubbyError, escaping, widget lifecycle, design tokens
platform.js14.3KBcorePocketBase: db, fs, ai, rooms, identity
markdown.js4.3KBcoresafe rendering
editor.js2.6KBmarkdowntextarea, live preview, paste-image upload
nav.js2.3KBcorethe sticky bar at the top of this page
preview.js2.8KBcorehover a link, see the page
draw.js4.4KBcorehold Alt and scribble; shared when signed in
graph.js5.3KBcorethe diagram above
foundation.js15.4KB—deprecated all-in-one; do not use it in new apps

This page loads core, platform, nav, draw, graph and preview. Hello loads all of them.

Tag order is the dependency declaration. defer scripts run in document order and there is no ready event, so this order is the whole contract — core first, your app last: 

<script src="/js/core.js" defer></script>
<script src="/js/platform.js" defer></script>
<script src="/js/markdown.js" defer></script>
<script src="app.js" defer></script>

As ES modules, import /js/platform.esm.js. /js/foundation.js is the deprecated all-in-one; it still works, but new apps should not use it.

Wait for cubby.ready, then use anything: 

await cubby.ready

cubby.app        // { name: 'myapp', base: '/myapp/' }
cubby.config     // the deployment's cubby.config.json
cubby.version    // foundation version

Every method throws cubby.CubbyError with a machine-readable .code: auth_required, not_found, bad_path, bad_request, model_unknown, provider_unconfigured, provider_error.

cubby.identity

OAuth2 only (Google and GitHub out of the box); password auth is disabled platform-wide. One users collection serves every app, and the session is shared across the origin automatically. 

cubby.identityChanged((user) => {
  render(user)                        // fires immediately; returns unsubscribe
})

await cubby.identity.login('github')  // popup flow
cubby.identity.user                   // user record | null
await cubby.identity.logout()

Identity changes propagate live: the foundation rebinds realtime subscriptions and lets subsystems clean up on logout. Apps only need identityChanged to re-render.

cubby.db

Collections are namespaced <app>_<name> by convention, and what you get back is the full PocketBase SDK record service: queries, pagination, expands, and realtime subscriptions all work as PocketBase documents them. 

const items = cubby.db.collection('items')      // -> '<app>_items'

await items.create({ title: 'hi' })
const page = await items.getList(1, 20, { sort: '-created', expand: 'user' })
await items.subscribe('*', (e) => { /* e.action, e.record */ })

cubby.db.collection('hello/guestbook')          // cross-app read
cubby.db.raw                                    // the PocketBase SDK client

App collections are created by real migrations committed with the app (default rules: read everyone, write authenticated). See Building an app.

cubby.fs

File storage over a shared platform collection: one record per (app, path), 10MB per file, public reads, authenticated writes, upsert semantics. 

await cubby.fs.write('notes/note.txt', 'hello')       // string | Blob | File
const text = await cubby.fs.read('notes/note.txt')
const url  = await cubby.fs.url('image.png')          // direct URL for <img src>
const list = await cubby.fs.list('notes/')            // [{ path, size, updated }]
await cubby.fs.remove('notes/note.txt')

await cubby.fs.read('data.json', { app: 'otherapp' }) // cross-app read

Files are shared per (app, path): for per-user data, put the user id in the path, like notes/${cubby.identity.user.id}.txt. write() also returns url, the direct file URL, so upload flows skip a round trip.

cubby.markdown

Markdown rendering and an editor with live preview and paste-image upload. Opt-in: one extra script tag after core.js (both defer, so order is guaranteed) — apps that skip it pay zero bytes. It needs core, not the platform: render() works with no backend at all. 

<script src="/js/core.js" defer></script>
<script src="/js/markdown.js" defer></script>
el.innerHTML = cubby.markdown.render('# hi **there**')

const ed = cubby.editor(container, {
  value: '',
  preview: true,                       // Write|Preview tabs; 'split' = live pane
  upload: { pathPrefix: 'uploads/' },  // paste/drop images upload via cubby.fs
  onUpload({ name, path, url }) {},
  onError(err) {},                     // auth_required when signed out
})
ed.value                               // get/set the markdown

The renderer is a dependency-free GFM subset (headings, emphasis, links, images, code, nested and task lists, tables, blockquotes) that escapes every source character at emission and vets URL schemes — raw HTML renders as visible text, so the returned string is safe to assign to innerHTML. Pasting an image inserts an ![Uploading…] placeholder that swaps to the real file URL when the upload lands, exactly like the GitHub PR editor. Uploads need a signed-in user and accept png/jpeg/gif/webp. See the markdown section of the hello app for it running live.

cubby.editor

A markdown textarea with a live preview and paste-image upload. Needs markdown.js before it; the platform is optional, and without one this is a plain composer with a working preview and upload silently off. 

<script src="/js/core.js" defer></script>
<script src="/js/markdown.js" defer></script>
<script src="/js/editor.js" defer></script>
const ed = cubby.editor('#editor', {
  value: '',
  preview: true,                       // Write|Preview tabs; 'split' = live pane; false = none
  upload: { pathPrefix: 'uploads/' },  // or false
  onChange(value) {}, onUpload({ name, path, url }) {}, onError(err) {},
})
ed.value          // live accessor
ed.setValue(md)
ed.images         // [{ name, path, url }] uploaded through this editor
ed.element; ed.preview; ed.textarea
ed.focus(); ed.refresh(); ed.destroy()

The preview renders through the same renderer the app uses for the saved value — cubby.markdown.render, read off the namespace at call time rather than bundled, so there is exactly one renderer on the page. What you see while typing is not an approximation of what gets stored.

A pasted image goes in as an ![Uploading…]() placeholder at the caret and is swapped for the real link when the upload lands, so the note keeps its shape while bytes are in flight. The stored path is built server-side from the user id and a token, so two pastes of the same image.png cannot collide.

cubby.ai

Chat through a server-side proxy; provider API keys live in instance secrets and never reach the browser. Models are friendly aliases defined in cubby.config.json (Anthropic, OpenAI, and Gemini supported), and anonymous calls are rejected. 

const res = await cubby.ai.chat({
  messages: [
    { role: 'system', content: 'answer briefly' },
    { role: 'user', content: 'what rhymes with cubby?' },
  ],
  model: 'claude-haiku',            // optional alias; omit for the default
  options: { maxTokens: 500 },
})

res.text                            // plus res.usage, res.model, res.provider

AI costs real money, so it is off until an app opts in: the app's cubby.json declares an ai.models allowlist (empty means blocked), calls are signed-in-only unless allowAnonymous is set, and each caller gets one prompt per rateLimitSeconds (default 60), enforced server-side. Optional hardening: allowedUsers email globs, input size caps, and messagePatterns (per-role regexes that turn prompts into fixed templates the browser cannot escape). Handle the error codes: model_not_allowed, user_not_allowed, content_not_allowed, content_too_long, rate_limited (with err.retryAfter seconds), and provider_unconfigured.

cubby.rooms

Presence, shared per-user state, and broadcast events for multi-user pages. Watching works signed out; joining requires auth and heartbeats automatically. A server-side sweeper cleans up after crashed tabs. 

const room = cubby.rooms.room('lobby')    // namespaced '<app>/lobby'

room.on('user.join',  (user) => {})
room.on('user.leave', (user) => {})
room.on('user.state', (prev, next, user) => {})
room.on('room.sync',  () => {})           // roster rebuilt; re-render here
room.on('wave',       (payload, user) => {})   // your own events

await room.watch()                        // observe only; works signed out
await room.join()
room.users                                // [{ user, state }]
await room.updateUserState({ score: 3 })
await room.emit('wave', { emoji: '👋' })
await room.leave()

Custom event names must not start with user. or room.. User names resolve for signed-in viewers only (profiles are auth-gated): render user.name || 'someone'. The presence pill in the corner of this page is cubby.rooms live.

cubby.nav

The sticky bar at the top of this page. Core only — no backend. Row one is the pages you declare plus a pinned action area that never scrolls; row two is the current page's sections. 

const bar = cubby.nav('#sitebar', {
  pages: [{ href: '/', label: 'Home' }, { href: '/docs/', label: 'Docs' }],
  sections: 'main',      // where to look (default: main, then body)
  globalRules: true,     // false to own scroll-margin-top / scroll-behavior yourself
})
bar.current()   // { page, section, actions } — actions is the pinned slot
bar.refresh()   // re-derive row two after rendering sections with JS
bar.destroy()

Row two is derived from the DOM, not declared. A section opts in by carrying aria-labelledby pointing at its own heading id: 

<section aria-labelledby="usage" data-nav-label="Usage">
  <h2 id="usage">Using the thing</h2>
</section>

That single id is the accessible name, the jump target and the nav label, so a nav entry pointing at a section that no longer exists is unrepresentable rather than merely unlikely. data-nav-label overrides a heading too long for a bar, and sections marked hidden are skipped — an entry that scrolls nowhere and never highlights reads as broken.

When the active section changes, its pill scrolls into view inside row two — only when it is actually off the end, and by setting scrollLeft on that one container rather than calling scrollIntoView, which walks every scrollable ancestor and can move the page itself.

The bar is position: fixed and reserves its own height on its mount element, so the page never starts underneath it. It measures itself once, publishes that as --cubby-nav-height, and re-measures on resize; the two global rules it leaks — scroll-margin-top on ids and :target, and smooth scrolling under prefers-reduced-motion: no-preference — read that property, so they cannot disagree with the bar's real height. current().actions is the pinned slot other widgets mount into.

cubby.preview

Hover a link, see the page. Core only. Delegated by default, so links rendered later need no re-wiring. 

const pv = cubby.preview(document.body, {
  selector: 'a[href]:not([href^="#"])',
  delay: 900,          // dwell before opening; applies to focus too
  scripts: false,      // true relaxes sandbox to allow-scripts
  allow: ['.example.com'],   // defaults to cubby.config.preview.frameable
})
pv.attach(el)   // wire a link outside the root; returns a disposer
pv.popover; pv.hide(); pv.destroy()

A frame blocked by X-Frame-Options or a frame-ancestors CSP cannot be detected from JavaScript. No error event fires, and load may still run on the blocked shell — so "try the iframe and fall back" is not implementable, and a reader would sit looking at a blank box. Framing is therefore an allowlist of hosts whose headers were actually measured, in cubby.config.json: 

curl -sI https://example.com/ | grep -iE 'x-frame-options|frame-ancestors'

Follow any redirect — it tells you nothing about the page you would land on — and record the date, because headers change. Same-origin is always frameable and never needs listing. A leading dot means "subdomain at any depth"; no dot is an exact host. A host that refuses still gets a card naming it: rendering nothing reads as a broken feature rather than as a page that will not embed. Frames are sandbox="" by default, and allow-same-origin is never paired with allow-scripts — together they let a framed document remove its own sandbox. See the live examples on Hello.

cubby.draw

Ephemeral shared cursors and freehand marks — hold Alt on this page and scribble. Uses cubby.rooms when the platform is loaded and degrades to a private highlighter when it is not. 

cubby.draw('main', {
  room: 'draw/page',   // default: one room per page
  modifier: 'alt',     // alt | ctrl | meta | shift
  cursors: false,      // broadcast your pointer to peers
  segmentMs: 800, fadeMs: 5000, strokeWidth: 3, opacity: 0.42,
})

A stroke is captured locally as a vector, simplified, and sent as whole paths — one event per time-boxed segment rather than as a stream of points. rooms.emit() writes a database row per call, so a 50ms point stream would be ~20 rows/sec per drawer; one path per ~800ms is roughly 1/sec. Segments flush on a timer as well as on release, so a peer's lag is bounded by the segment rather than by how long you keep drawing, and each carries its duration so the receiver replays it at the speed it was drawn.

The local puck always shows, even with no backend; broadcasting your cursor to peers is off by default, because every sample is a presence write and an SSE fan-out. Sharing needs sign-in. Nothing is persisted in any way that is ever read back: clients subscribe to create only, so a late joiner sees nothing and a refresh clears the page.

cubby.graph

Node-and-edge diagrams in inline SVG — the one above is built with it. Core only, zero dependencies: no d3, no mermaid, no canvas, because a static-files-only site cannot afford a renderer script. 

cubby.graph('#diagram', {
  lanes: [{ id: 'browser', label: 'Browser' }],
  nodes: [{ id: 'app', lane: 'browser', column: 1, label: 'app.js', note: 'markdown **note**' }],
  edges: [{ id: 'e1', from: 'app', to: 'api', kind: 'http', label: 'REST' }],
  journeys: [{ id: 'load', label: 'Load a page', hue: 205, edges: ['e1'] }],
  kinds: { http: { hue: 205, dash: '' }, data: { hue: 145, dash: '7 4' } },
})

Declarative data with no coordinates. Lanes give y, column gives x, and one pass computes the rest. There is no force simulation: a diagram that rearranges itself between visits cannot be referred to in prose. column is 1-based and unique within a lane, which makes layout a direct mapping rather than a packing problem.

A journey is a list of edge ids, never node ids. It can then only describe hops that were actually declared, and "every node no journey touches" becomes derived instead of maintained — the two cannot disagree. A node no journey touches falls back to its own edges when highlighted, or hovering it would dim everything and highlight nothing.

Plain wheel scrolls the page; only ⌘/Ctrl + wheel zooms. Everything reachable by hover is reachable by focus with the same highlight, and every journey is written out as prose beneath the canvas — the drawing is never the only copy. Edge kinds differ by dash as well as hue, so the diagram survives greyscale printing and colour vision differences.

Building an app

An app is one directory served at /<name>/:

pb_public/myapp/
├── index.html      loads /js/core.js + /js/platform.js + app.js
├── app.js          await cubby.ready, then build
├── style.css
└── cubby.json      { name, title, description, icon }   -> discovery site card

Scaffold one (or ask Claude via /cubby:new-app):

npm run new-app myapp -- --title "My App" --icon "🎯"
npm run dev         # local PocketBase + watch build at localhost:8090

Three rules keep everything working:

  • Hash routing. Unknown server paths fall back to the discovery site, so internal navigation uses #/page, never real paths.
  • Own your prefix. Collections you create are myapp_*, added via a migration file committed with the app; read anything, write only yours.
  • Do not touch the platform. The foundation, hooks, platform migrations, and other apps stay as upstream ships them. That is what keeps platform updates a clean merge.

Running your own

The public repo is a GitHub template and the platform's home. Your deployment is a separate repo created from it; apps live there, and platform improvements flow back upstream. The five-step version:

  1. Create an instance at pockethost.io.
  2. Install the plugin (see above).
  3. /cubby:init you/your-repo: creates the repo, clones the platform with shared history, fills cubby.config.json (name, domain, instance URL), pushes.
  4. /cubby:deploy: links the instance, first deploy, and walks you through OAuth apps, AI keys, and secrets.
  5. Add PHIO_USERNAME, PHIO_PASSWORD, and PHIO_INSTANCE_NAME as repo secrets and every push to main deploys automatically: the bundled workflow rebuilds, verifies, and syncs to PocketHost.

From then on it is a loop: idea, /cubby:new-app (or a new-app labeled issue from your phone), merge, live. Platform updates arrive with /cubby:update, which merges upstream and redeploys; your config and apps are never touched by it.
