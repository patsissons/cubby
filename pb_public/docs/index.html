📚 Cubby, on one page

A shelf of tiny web apps, each in its own cubby. This page is everything you need to understand the platform, use its APIs, and run your own. It is itself a cubby app.

In a nutshell

One GitHub repo deploys to one PocketHost (PocketBase) instance and hosts many tiny static web apps. Each app is a directory of plain html/js/css: no build step, no framework, no server code of its own.

repo
pb_public/<app>/ + hooks + migrations
deploys to
instance
<name>.pockethost.io
serves
/<app>/
+ / discovery site

Every app loads one script and gets the whole platform:

<script src="/js/foundation.js" defer></script>

That script exposes a global cubby object providing a database (db), file storage (fs), OAuth login (identity), AI chat (ai), and multi-user rooms (rooms), all backed by the shared PocketBase instance. The root of every deployment is a discovery site listing its apps. Login state is shared across all apps on the origin: sign in once, signed in everywhere.

What it's good for

Weekend-sized ideas that deserve to stay alive: guestbooks, timers, trackers, polls, little games, dashboards, gifts. Anything where "a static page plus a database plus login" covers it, and where shipping in an afternoon beats architecture. New app cost is one directory, so nothing stops you from having thirty of them.

Honest constraints, by design:

  • Rooms ride PocketBase realtime over SSE: expect 100-500ms latency. Chat, presence, and casual multiplayer are great; twitch gameplay is not.
  • AI chat is non-streaming (the server hook buffers whole responses).
  • Apps are static files; anything dynamic goes through the foundation APIs.
  • Write isolation between apps is convention, not enforcement: a single-operator platform.

The Claude plugin

The repo is its own Claude Code plugin marketplace. The skills that power it are the same documents an AI agent follows, so "ask Claude to do it" is a first-class path: 

/plugin marketplace add patsissons/cubby
/plugin install cubby@cubby
/cubby:initbootstrap a deployment repo: create, clone with shared history, wire remotes, fill cubby.config.json, push
/cubby:deploystand up the instance: phio link, first deploy, OAuth, keys, CI secrets
/cubby:new-appscaffold and build a new app in an existing deployment
/cubby:updatemerge upstream platform updates into a deployment and roll them out

There is also an issue-to-app pipeline: label a GitHub issue new-app and a bundled workflow has Claude build it as a pull request; merging deploys it. Idea on your phone to live app, no laptop involved.

The foundation

Load /js/foundation.js (or import /js/foundation.esm.js), wait for cubby.ready, then use anything: 

await cubby.ready

cubby.app        // { name: 'myapp', base: '/myapp/' }
cubby.config     // the deployment's cubby.config.json
cubby.version    // foundation version

Every method throws cubby.CubbyError with a machine-readable .code: auth_required, not_found, bad_path, bad_request, model_unknown, provider_unconfigured, provider_error.

cubby.identity

OAuth2 only (Google and GitHub out of the box); password auth is disabled platform-wide. One users collection serves every app, and the session is shared across the origin automatically. 

cubby.identityChanged((user) => {
  render(user)                        // fires immediately; returns unsubscribe
})

await cubby.identity.login('github')  // popup flow
cubby.identity.user                   // user record | null
await cubby.identity.logout()

Identity changes propagate live: the foundation rebinds realtime subscriptions and lets subsystems clean up on logout. Apps only need identityChanged to re-render.

cubby.db

Collections are namespaced <app>_<name> by convention, and what you get back is the full PocketBase SDK record service: queries, pagination, expands, and realtime subscriptions all work as PocketBase documents them. 

const items = cubby.db.collection('items')      // -> '<app>_items'

await items.create({ title: 'hi' })
const page = await items.getList(1, 20, { sort: '-created', expand: 'user' })
await items.subscribe('*', (e) => { /* e.action, e.record */ })

cubby.db.collection('hello/guestbook')          // cross-app read
cubby.db.raw                                    // the PocketBase SDK client

App collections are created by real migrations committed with the app (default rules: read everyone, write authenticated). See Building an app.

cubby.fs

File storage over a shared platform collection: one record per (app, path), 10MB per file, public reads, authenticated writes, upsert semantics. 

await cubby.fs.write('notes/note.txt', 'hello')       // string | Blob | File
const text = await cubby.fs.read('notes/note.txt')
const url  = await cubby.fs.url('image.png')          // direct URL for <img src>
const list = await cubby.fs.list('notes/')            // [{ path, size, updated }]
await cubby.fs.remove('notes/note.txt')

await cubby.fs.read('data.json', { app: 'otherapp' }) // cross-app read

Files are shared per (app, path): for per-user data, put the user id in the path, like notes/${cubby.identity.user.id}.txt.

cubby.ai

Chat through a server-side proxy; provider API keys live in instance secrets and never reach the browser. Models are friendly aliases defined in cubby.config.json (Anthropic, OpenAI, and Gemini supported), and anonymous calls are rejected. 

const res = await cubby.ai.chat({
  messages: [
    { role: 'system', content: 'answer briefly' },
    { role: 'user', content: 'what rhymes with cubby?' },
  ],
  model: 'claude-haiku',            // optional alias; omit for the default
  options: { maxTokens: 500 },
})

res.text                            // plus res.usage, res.model, res.provider

Handle provider_unconfigured gracefully: not every deployment sets every provider's key. Unknown aliases throw model_unknown before any request.

cubby.rooms

Presence, shared per-user state, and broadcast events for multi-user pages. Watching works signed out; joining requires auth and heartbeats automatically. A server-side sweeper cleans up after crashed tabs. 

const room = cubby.rooms.room('lobby')    // namespaced '<app>/lobby'

room.on('user.join',  (user) => {})
room.on('user.leave', (user) => {})
room.on('user.state', (prev, next, user) => {})
room.on('room.sync',  () => {})           // roster rebuilt; re-render here
room.on('wave',       (payload, user) => {})   // your own events

await room.watch()                        // observe only; works signed out
await room.join()
room.users                                // [{ user, state }]
await room.updateUserState({ score: 3 })
await room.emit('wave', { emoji: '👋' })
await room.leave()

Custom event names must not start with user. or room.. User names resolve for signed-in viewers only (profiles are auth-gated): render user.name || 'someone'. The presence pill in the corner of this page is cubby.rooms live.

Building an app

An app is one directory served at /<name>/:

pb_public/myapp/
├── index.html      loads /js/foundation.js + app.js
├── app.js          await cubby.ready, then build
├── style.css
└── cubby.json      { name, title, description, icon }   -> discovery site card

Scaffold one (or ask Claude via /cubby:new-app):

npm run new-app myapp -- --title "My App" --icon "🎯"
npm run dev         # local PocketBase + watch build at localhost:8090

Three rules keep everything working:

  • Hash routing. Unknown server paths fall back to the discovery site, so internal navigation uses #/page, never real paths.
  • Own your prefix. Collections you create are myapp_*, added via a migration file committed with the app; read anything, write only yours.
  • Do not touch the platform. The foundation, hooks, platform migrations, and other apps stay as upstream ships them. That is what keeps platform updates a clean merge.

Running your own

The public repo is a GitHub template and the platform's home. Your deployment is a separate repo created from it; apps live there, and platform improvements flow back upstream. The five-step version:

  1. Create an instance at pockethost.io.
  2. Install the plugin (see above).
  3. /cubby:init you/your-repo: creates the repo, clones the platform with shared history, fills cubby.config.json (name, domain, instance URL), pushes.
  4. /cubby:deploy: links the instance, first deploy, and walks you through OAuth apps, AI keys, and secrets.
  5. Add PHIO_USERNAME, PHIO_PASSWORD, and PHIO_INSTANCE_NAME as repo secrets and every push to main deploys automatically: the bundled workflow rebuilds, verifies, and syncs to PocketHost.

From then on it is a loop: idea, /cubby:new-app (or a new-app labeled issue from your phone), merge, live. Platform updates arrive with /cubby:update, which merges upstream and redeploys; your config and apps are never touched by it.
